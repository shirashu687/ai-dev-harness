# ai-dev-harness — AI開発の共通作業手順

既存のGitリポジトリに、AIが使う**作業手順・検証と報告・引継ぎ・改善記録**を加えます。「実装は進んだが何を確認したか分からない」「別セッションで再開すると調査からやり直す」といった場面で、確認結果と次の作業を残すための仕組みです。

配布物の中心はMarkdownの手順書とテンプレートです。AIが既存のテストや開発ツールと組み合わせて使います。このリポジトリは仕様・配布物の管理場所で、導入先は**あなたが開発するプロジェクト**です。

## できること・できないこと

| できること | 使い方・得られるもの |
| --- | --- |
| 作業に合う進め方を選ぶ | 小・通常・大に分け、小さな修正は直接実装、判断が多い作業は計画・レビューへ進む |
| 検証の実態を残す | 対象版と実行コマンドを添え、成功・失敗・未実行・実行不能を区別して報告する |
| 別セッションへ引き継ぐ | 作業記録に目的・変更・検証・妨げ・次の一手を残して再開する |
| 繰り返す問題を改善へつなぐ | 必要なときに振り返り、根拠・改善候補・試行を台帳に残す |
| 複数プロジェクトで共通手順を使う | 手順は共通化し、テストコマンドや既存文書への対応は各プロジェクトで設定する |
| 配布版を照合して保守する | 固定Gitコミットと導入記録を使い、導入・更新・巻戻し・撤去の前後を確認する |

以下は提供していません。

- **一括インストーラー、専用CLI、公開プラグイン。** 現在はAIまたは人が明示手順を実行します。`tests/test_distribution.py` は照合器と一時環境のテストです。
- **常駐実行、自動更新、定時の振り返り。** AIに作業を依頼した際に手順を読み、実行する運用です。
- **全プロジェクト共通のCI・権限ガード・テスト。** 既存の仕組みへ接続します。文書だけでは禁止操作の阻止や報告の正しさを保証しません。
- **上流スキルの一括同梱。** ガイドにあるスキル名は候補です。採用するスキルは別に導入し、未導入のものを利用可能とは扱いません。
- **品質・開発速度・完全自律の保証。** 導入実績と、改善効果の測定結果は別です。製品・環境ごとの確認も必要です。

<a id="getting-started"></a>

## 導入する

### 1. 導入先を用意する

まずはテストを実行できる小さな既存プロジェクトで試してください。用意するものは次のとおりです。

- **導入先のGitリポジトリ**と、変更を確認・取り消せる作業ブランチまたは作業用コピー。
- **リポジトリのファイルを読み書きし、コマンドを実行できるAI開発環境。** 実証範囲は[後述](#validation)を参照してください。
- **Git、Python 3、配布元GitHubへのアクセス。** 配布テストはPython標準ライブラリを使います。掲載の手動操作例はPowerShell形式です。
- **対象アプリの依存関係とテスト実行環境。** テスト・lint等のコマンドが分かればAIへ伝え、不明なら既存設定から調べてもらいます。

上流スキルを採用する場合は、その導入手段の依存関係も別途必要です。OKF・Obsidianは任意であり、非OKFのプロジェクトにも接続できます。

### 2. 導入先をAIで開き、この依頼文を渡す

```text
https://github.com/shirashu687/ai-dev-harness のREADMEを入口に、このリポジトリへ共通ハーネスを導入してください。推奨配布版と検証根拠を確認し、既存の構成・入口・必要検証を調べて、固定版の導入手順を実行してください。上流スキルと自前コアを別の依存として扱い、対象版・変更内容・検証結果と未確認範囲を記録してください。
```

AIは[版の解決手順](docs/project/harness-distribution.md#resolve-versions)に従い、既存差分の確認、固定版の取得、退避、設定と入口の接続、検証、導入記録の照合を行います。実装コードを先に読む必要はありません。人が操作する場合も[導入・保守手順](docs/project/harness-distribution.md)を使えます。

既存の指示・ファイルとの競合、利用できない実行環境、出所を確認できない版は、解決が必要な点として報告されます。コピーできただけの状態を導入成功とは扱いません。

### 3. 導入結果を確認する

| 導入先の場所 | 何が入るか・確認すること |
| --- | --- |
| `AGENTS.md`（必要なら `CLAUDE.md`） | 既存の指示を保持したまま共通ガイドへ接続している |
| `harness/core/` | 作業ガイド、必須制約、検証・引継ぎ・振り返り手順、作業記録の雛形。配布元が管理する6ファイル |
| `harness/project/config.md` | このプロジェクトの文書・テストコマンド・制約の強制点と限界が記入されている |
| `harness/project/skill-profile.md` | 採用済みスキルと候補、製品ごとの確認状態を区別している |
| `harness/ledger.md` | 改善台帳。初期状態で改善実績がなくても正常 |
| `harness/install.json` | 配布元・完全SHA・管理ファイルのハッシュが記録され、配布版と照合できる |
| `harness/state/journal/` | 作業時に記録を置く場所。空のディレクトリが初回から存在する必要はない |
| 導入先のライセンス通知 | 本ハーネスと、採用した第三者スキルの通知が保持されている |

検証報告には対象プロジェクトの必須検証と未確認範囲が必要です。`config.md` の必須欄が未設定、または必要な検証が失敗・未実行・実行不能なら、残った準備を解消してから利用確認へ進みます。

<a id="first-task"></a>

## 最初に試すこと

**READMEの誤字や既存コマンドの説明を1か所直す**ところから始めます。下の依頼文の修正内容を、実際の小さな変更に置き換えてください。

```text
このリポジトリの入口とハーネスの設定を読み、READMEの「<修正箇所>」を「<期待する内容>」へ修正してください。作業の重さを判断し、設定された必須検証を実行してください。最後に変更内容、検証の成功・失敗・未実行・実行不能、残っていることを短く報告してください。
```

見るポイントは、AIが**実際の設定を読んだか、必要な検証を行ったか、できなかった確認を明示したか**です。小作業では計画書・通常の作業記録を省略できるので、文書が大量に生成されることを成功条件にしません。

次に、小さな不具合修正で作業記録を作り、別セッションから再開すると引継ぎを試せます。依頼例と期待結果は[日常の使い方](docs/project/harness-usage.md)を参照してください。

## 推奨配布版

版指定のない依頼では、次の記録を使います。

| 項目 | 記録 |
| --- | --- |
| 提供状態 | 提供中（2026-09-07確認） |
| 推奨する完全GitコミットSHA | `898d514f0594ff09f6c19292ef4df56f6cc4ac50` |
| 検証根拠 | [T-0013の確定記録](https://github.com/shirashu687/ai-dev-harness/blob/e04e3dae2ab6f797def69a3a6c541ca0b5a643c6/docs/backlog/T-0013-extract-distributable-core.md): 正式GitHubからの独立取得、11ファイルの配布境界、5操作と復旧の演習、okf-devkitへの移行・保持検証 |
| 今回の再確認 | [T-0014の検証記録](docs/backlog/T-0014-ai-distribution-entry.md): 固定版の取得・内容・手順参照と文書入口の確認 |
| 推奨を取り下げた版・問題 | 記録なし（2026-09-07時点） |

これは導入・更新先の推奨です。導入済みの現在版は対象リポジトリの `harness/install.json` から確認します。取得方法と同版時の扱いは[版の解決手順](docs/project/harness-distribution.md#resolve-versions)を参照してください。

推奨版の変更・取り下げ・保守休止・提供終了は、管理者が必要時に [HARNESS_SPEC.md](HARNESS_SPEC.md) §9.1.4に従ってこの欄へ反映します。版指定のない依頼はこの欄が「推奨版なし」または「提供終了」の場合、版の解決で止まります。既存導入への自動更新はありません。

## 配布と検証の範囲

配布対象は、選んだ固定版の `distribution/manifest.json` に列挙した共通コアと初回用の雛形です。上流スキルは各プロジェクトから直接導入します。README・仕様書・リポジトリ全体を導入先へコピーする必要はありません。

| 確認対象 | 記録されている結果 |
| --- | --- |
| 固定版の取得と配布操作 | 正式GitHubからの取得、11ファイルの境界、5操作と復旧の一時環境演習。[T-0013](docs/backlog/T-0013-extract-distributable-core.md) |
| okf-devkit | 共通コアへの移行と固有データ保持を確認。製品利用の記録は [T-0008](docs/backlog/T-0008-pilot-two-products.md)、配布移行は [T-0013](docs/backlog/T-0013-extract-distributable-core.md) |
| ScheLiveApp | コア・上流を分けた導入、隔離演習、Codex実利用、ローカル必須検証を確認。Claude Code実利用やホスト上の最終CIは今回の確認外。[T-0009](docs/backlog/T-0009-second-repository-rollout.md) |
| URL付き依頼の入口 | 固定版・参照・同版照合を確認。[T-0014](docs/backlog/T-0014-ai-distribution-entry.md)。README公開後のURL入口を通した実導入体験と負担軽減は未確認 |

一時環境での成功を、あなたのプロジェクトでの導入成功とは読み替えません。開発速度や手戻りの改善効果も未認定です。

## 更新・巻戻し・撤去

AIには[更新の依頼文](docs/project/harness-distribution.md#ai-update)を渡してください。共通コアの更新と上流スキルの更新は別操作です。巻戻し・撤去・途中失敗の復旧は[導入・保守手順](docs/project/harness-distribution.md)にあります。

普段の調整は `harness/project/` へ書きます。管理対象の `harness/core/` を直接編集すると更新前の照合で止まるため、共通手順の変更は配布元へ還元します。

## このリポジトリを開発する人へ

配布物のテストはリポジトリルートで実行します（Python 3.12での検証記録があります）。GitもPATHに必要です。

```shell
python -B -m unittest discover -s tests -p test_distribution.py
```

このコマンドは一時Gitリポジトリを作って検査します。プロジェクトへの導入コマンドではありません。文書編集の規約とOKFによる検査は [AGENTS.md](AGENTS.md) と [docs/AGENTS.md](docs/AGENTS.md) を参照してください。配布物を利用するだけならOKF CLIの導入は不要です。

仕様の正本は [HARNESS_SPEC.md](HARNESS_SPEC.md)、実装・実証の進捗は [バックログ](docs/backlog/index.md) にあります。

01 / DEFINITION

スキルはハーネスの一部。
本体は「制御ループ」

コーディングエージェント向けの外側のハーネスは、よい結果へ先回りして導くものと、実行後の誤りを検知して直させるものの組み合わせとして捉えると分かりやすい。

YES

この取り組みは、十分にハーネスエンジニアリングと呼べます。

ただし境目は「スキルを何個入れたか」ではありません。人が意図を示し、エージェントが実行し、テストやレビューが結果を観測し、繰り返す失敗を環境へ戻す——この循環を設計・改善しているかどうかです。

1

Guide / 導く

AGENTS.md、OKF文書、ADR、スキルで、目的・制約・進め方を先に渡す。

2

Execute / 実行

エージェントが調査、設計、実装、修正を行う。mattpocock/skillsが主に強い領域。

3

Sense / 観測

テスト、型、lint、CI、ログ、レビューで、期待との差を具体的な信号にする。

4

Learn / 学習

振り返りを候補として記録し、再発を見て試行・採用・却下・廃止する。

観測された再発だけを、よりよいガイドや機械的チェックへ戻す

全部を自作する必要はありません。ただし所有と更新は混ぜません。再利用できる能力は各対象リポジトリがmattpocock/skillsから直接導入し、プロジェクト契約だけを自前で持ちます。

人間の操舵

自前の薄い層

入口、プロジェクト固有の検証・報告契約、改善台帳、採用ゲート、CI等の強制点、製品差のアダプター。

プロジェクトのテスト、型検査、lint、構造検査、CI、ログ・メトリクス、必要に応じたエージェントレビュー。

03 / COVERAGE

何が既にあり、
何を自前で足すのか

「無い」と言い切るより、完成形まで含むかで判定するのが正確です。隣接するスキルはあっても、プロジェクト固有の制御としては未完成な領域があります。

機能 判定 mattpocock/skillsにあるもの 追加するもの
入口とルーティング カバー ask-matt が主要フロー、分岐、単独スキルを案内。 人間向けの日本語一覧があれば十分。
詳細化・仕様・分割 カバー grill-with-docs、prototype、to-spec、to-tickets、domain-modeling。 対象プロジェクトの文書配置だけ接続。
実装・TDD・レビュー・診断 カバー implement が tdd と code-review を使用。難しい不具合には diagnosing-bugs。 各リポジトリの実コマンドと合格条件。
プロジェクト固有の検証・完了報告 自前 implement に一般的な型検査・テスト指示はある。handoff は別エージェント向け引継ぎ。 変更種別→実行コマンド、未実施理由、結果、残存リスクを揃えた短い報告契約。
振り返りの分析 部分 retro が環境改善の候補を分類し、重要度順に提示。ただし現在は上流のin-progress。 初期プロファイルからは外し、毎回実行するかのゲートと、候補を一旦保留する運用を自前で置く。
改善台帳のライフサイクル 自前 永続台帳、同一症状の集約、件数上限、保持期限は定義されていない。 観測 → 候補 → 試行 → 採用 / 却下 / 廃止、再発回数、最大10件など。
規則への昇格・除去ゲート 自前 retro は候補提示までで、ルール変更の承認や評価比較は持たない。 一度の失敗では恒久化しない、試行期限、効果比較、廃止条件。安全上の例外のみ即時。
機械的な強制 部分 setup-pre-commit やGitガードレールなど個別部品はある。 プロジェクトのCI・lint・型・権限へ、どの規則をどこで強制するかの対応表。
Codex / Claude Code差の吸収 部分 多くは移植可能だが、/clear、Skill tool、Claude固有hookなどの表現が残る。 製品ごとの呼び出し・権限・hook・一時ファイルの差だけを薄いアダプターにする。

質問への短い答え： はい、以前挙げた「自前部分」の中心はmattpocock/skillsに完成品としては入っていない、という認識で合っています。

上流スキルは能力、自前部分はプロジェクト契約です。上流を一括フォークするのではなく、外側に小さな台帳・検証契約・昇格ゲートを足すのが保守しやすい構成です。

04 / WORKFLOW

全タスクを同じ重さにしない

グリリング、仕様書、チケット、完全な振り返りを毎回強制すると、軽い変更まで重くなります。仕事の大きさと不確実性で入口を変え、検証と報告だけは共通にします。

小さい明確・低リスク
implement› 検証・報告
摩擦があった時だけretroへ。
通常判断が少し必要
ask-matt› grill› implement + TDD + review› 検証・報告
最後にretroゲートを判定。
大きい複数セッション
grill› prototype?› to-spec› to-tickets› implement × N› 統合検証・報告
判断点と証拠を残し、必要ならfull retro。

振り返りは「記録」ではなく「昇格フィルター」にする

1 · OBSERVE今回の摩擦を短く記録
2 · GROUP同じ症状なら件数を加算
3 · CANDIDATEretroで改善案を作る
4 · TRIAL期限付きで小さく試す
5 · DECIDE採用・却下・廃止
6 · PROMOTE文書、skill、検査へ昇格

full retroの目安： 人が修正した／同じ探索を繰り返した／検証漏れがあった／ツールやコンテキストに大きな摩擦があった／高コスト・高リスクだった。何も起きていない回は5行程度の完了要約で十分。

05 / OBSIDIAN

Obsidianは「記憶装置」より
人間向けの読書・探索画面

Obsidianはローカルフォルダ内のMarkdownをそのままノートとして扱います。専用データベースへ閉じ込めず、エディタやGitとも同じファイルを共有できます。

HUMAN VIEW

Obsidian

検索、バックリンク、グラフ、プロパティ表示で、人間が知識間のつながりを見つける。

DOCUMENT CONTRACT

OKF

frontmatter、語彙、index、関連、検証状態、stale判定を機械的に揃える。

SYSTEM OF RECORD

Markdown + Git

人とエージェントが直接読める正本。差分、履歴、レビュー、復元を担う。

Obsidian ≠ 別の知識庫　／　Obsidian = 同じ正本を見る窓

この構成で使うなら

  • リポジトリ自体をVaultとして開き、Markdownの正本を重複させない。
  • OKFの related やMarkdownリンクを育てる。グラフは「リンクを作った結果」として使う。
  • .obsidian/workspace*.json など個人の画面状態は原則Git管理外。共有する設定だけを選ぶ。
  • 振り返りを無制限に保存しない。台帳は活動中を最大10件程度にし、同じ症状は新規ノートではなく件数を増やす。

この方針ではObsidianを利用する。ただしハーネスの実行条件にはせず、Obsidianがない環境でも同じMarkdownとGitだけで動く状態を保つ。

06 / LANGUAGE

全文翻訳より、
日本語の案内層を足す

日本語だから精度が下がる、という単純な関係ではありません。ただし全文翻訳は上流更新とのズレを生み、スキルの起動条件や強い表現のニュアンスを変える可能性があります。

推奨：原文 + 日本語カタログ

  • 上流の SKILL.md はまず英語のまま保つ
  • 目的、使う場面、呼び出す先を日本語で1枚に整理
  • プロジェクト固有の入口・検証・報告は日本語で書いてよい
  • 誤起動が出る場合だけdescriptionを日英併記し、実タスクで比較

慎重に：全スキルの一括翻訳

  • 上流更新を毎回追従する翻訳フォークになる
  • must / should、例外、起動条件の意味がずれる可能性
  • どの変更が動作差を生んだか分かりにくい
  • 翻訳するなら代表タスクで原文版と結果を比較する

08 / FIRST ITERATION

実装はこの順で進める

最初の適用先はokf-devkit。上流依存の境界から固め、最後に実作業で有効性を確認します。後続タスクは着手直前にだけ詳細化します。

1 · 直接依存

ask-mattの参照が閉じたプロファイルを選び、重複・lock・ライセンスを確認。

2 · 日本語入口

短い入口と、目的・対象外・呼出関係が分かる日本語ガイドを設置。

3 · 完了契約

規模別フロー、4値の検証・報告、引継ぎ、実在する強制点を接続。

4 · 学習ループ

retroゲートと最大10件の改善台帳を置き、一度の失敗を即ルール化しない。

5 · Obsidian / OKF

リポジトリをVaultとして開き、同じMarkdownを索引・検索・リンクで扱う。

6 · 実証

3件の代表作業をClaude CodeとCodexで流し、品質・手戻り・起動精度を比較。

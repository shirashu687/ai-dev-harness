# 共通ハーネスの最初の作業と日常の使い方

この文書は導入後に使う人向けの案内です。導入前は [README](../../README.md#getting-started) から始めてください。以下の `harness/` パスはすべて**導入先リポジトリ**を指します。例の `<...>` は実際の作業内容に置き換えます。

## 1. 最初は小さな変更を1件試す

READMEの誤字、既存のテストコマンドの説明など、期待する結果が明確な変更を選びます。導入先をAIで開いて依頼します。

```text
このリポジトリの入口とハーネスの設定を読み、READMEの「<修正箇所>」を「<期待する内容>」へ修正してください。作業の重さを判断し、設定された必須検証を実行してください。最後に変更内容、検証の成功・失敗・未実行・実行不能、残っていることを短く報告してください。
```

確認するのは次の3点です。

1. 入口から `harness/core/guide.md` と `harness/project/config.md` に進み、対象の設定を使っている。
2. 依頼した範囲の差分になり、設定された必須検証を実行している。
3. 最終報告で変更内容と検証結果を区別し、実行していない確認を成功としていない。

小作業では通常の作業記録・計画書を省略できます。既存テストは省略対象ではありません。途中で中断する場合は、小作業でも次節の作業記録を残します。

## 2. 通常の不具合修正・機能追加を依頼する

複数の判断や振る舞い変更がある作業では、目的・対象外・完了条件を作業記録に残します。先に全スキルを指定する必要はありません。

```text
<実際の症状または追加したい機能> に対応してください。
期待する結果は <利用者から見た振る舞い> です。
今回は <対象外の変更> を含めません。
ハーネスの入口と設定に従って進め、作業記録に開始時の比較点・完了条件・検証結果を残してください。
```

AIは `harness/core/templates/worklog.md` を基に、設定された場所へ作業記録を作ります。標準の場所は `harness/state/journal/<task-id>.md` です。仕様とリポジトリの規約を別々の観点でレビューし、必須検証を実行します。

実行に使えるスキルは `harness/project/skill-profile.md` の採用済み一覧から確認します。ガイドに名前があっても未導入なら、そのスキルを使ったことにはしません。TDDもすべての編集に一律適用する手順ではありません。

作業後は差分と最終報告を確認します。報告には完了条件との対応、検証結果、レビュー、残っている問題が必要です。詳細な証拠は作業記録を参照します。

## 3. 中断して、別セッションで再開する

まず作業中のAIへ依頼します。

```text
この作業をいったん中断します。ハーネスの引継ぎ手順に従い、作業記録を更新してください。変更済みの内容、最新の検証結果、妨げ、前提、次の一手を残し、記録のパスを教えてください。
```

同じ導入先リポジトリを新しいAIセッションで開き、返されたパスを渡します。

```text
このリポジトリの入口と <作業記録のパス> を読み、ハーネスの再開手順に従って作業を続けてください。記録と現在のGit差分・検証状態を照合してから、次の一手へ進んでください。
```

引継ぎで残すのは会話全文ではなく、再開に必要な作業状態です。記録後に変更が加わっていれば、以前の検証成功が現状にも成立するか確認します。新しい担当が目的・残作業・次の操作を特定できれば、引継ぎの確認になります。

## 4. 振り返りと改善台帳を使う

通常・大の作業の完了時や中断時に、AIが振り返りの要否を判定します。full retrospective（詳しい振り返り）は毎回実施せず、手順に定められた問題の兆候がある場合に進みます。判定の詳細は導入先の `harness/core/procedures/retrospective.md` にあります。

問題を伝える場合は、実際の観測を添えます。

```text
今回 <同じ確認を繰り返した／検証結果と報告が食い違った等の具体的な出来事> がありました。作業記録と差分を照合して振り返りの要否を判断し、必要なら根拠と改善候補を改善台帳に残してください。
```

台帳は `harness/ledger.md` です。候補が書かれただけでは改善を採用したことになりません。AIが定期起動して自動的にルールを書き換える機能でもありません。

## 5. プロジェクトの設定を変える

| 変わったこと | 更新する場所 |
| --- | --- |
| テストコマンド・実行場所・CI・制約の強制点 | `harness/project/config.md` または、そこから参照する既存の正本 |
| 仕様・課題・ドメイン文書の配置 | `harness/project/config.md` の役割対応 |
| 採用スキル・実効配置・製品での確認状態 | `harness/project/skill-profile.md`。導入版の正本がlock等にある場合は参照する |
| 作業の現在地 | 該当する作業記録 |
| 改善の観測・候補・試行 | `harness/ledger.md` |

`harness/core/` は固定版と照合する配布元管理の領域です。直接の書換えでプロジェクトに合わせず、固有設定で対応します。共通手順自体を変える必要がある場合は、配布元の仕様・配布物の変更として扱います。

## 6. 期待どおりに動かないとき

| 状況 | 最初に確認すること |
| --- | --- |
| AIがハーネスを読まない | 開いたリポジトリが導入先か、実際に読む入口からガイドとconfigへ辿れるか。ファイル配置と製品での利用確認は別 |
| テストを実行できない | configのコマンド・実行場所・依存関係。実行不能として理由と再実行条件を残す |
| ガイドのスキルを呼び出せない | profileの採用済み一覧・実効配置・確認済み製品。候補一覧だけでは導入済みにならない |
| 小さな修正でも大きな計画を始める | ガイドの小・通常・大の判断と、依頼の変更範囲・期待結果 |
| 更新前の照合で止まる | コアの手修正・欠落・未知ファイル・導入記録の不整合。差分を確認し、記録を消して新規導入に偽装しない |
| 導入や更新の途中で失敗した | 操作時の退避と変更記録を使い、[保守手順](harness-distribution.md) §9で今回の変更を復旧する |

更新・巻戻し・撤去も[保守手順](harness-distribution.md)から実行します。コアの更新で、既存の設定・作業記録・台帳・上流スキルを一括置換しません。

# 自立継続運用の仕組みを設計・検証する
## やりたいこと

導入後のハーネスが、人手の常時監視や都度の再実行に依存せず継続して動く仕組みを設計・検証する。実行、状態確認、失敗時の通知・再試行、停止・更新・撤去までを一つの運用契約として定める。

## 背景・現状

現行仕様は、入口から実装、検証、報告、retro、改善台帳までの開発作業ループを定義しているが、作業の外側でハーネス自身を定期的・継続的に動かす実行主体は定義していない。上流スキルの更新も対象リポジトリごとの明示実行が前提であり、更新確認、ヘルスチェック、滞留作業の検知、停止判断を誰がいつ行うかが未確定である。

自立性を優先しすぎると、意図しない変更、無制限な再試行、権限の拡大、API・CIコストの増加、古い状態のまま動き続ける危険がある。そのため「常時無人で変更を承認する」ことではなく、可逆な定期処理と観測を自動化し、不可逆な判断・権限変更・公開・削除は人間の承認境界に残す必要がある。

## 進め方

1. `okf-devkit` と `ScheLiveApp` の実行環境、利用可能なスケジューラ、認証方式、ネットワーク制約、許容コストを調査する。
2. 継続運用の状態モデルを定める。少なくとも、未実行、実行中、成功、失敗、再試行待ち、停止、要承認、期限切れを区別し、実行ID・開始時刻・終了時刻・入力版・結果・次回実行を追跡できるようにする。
3. 定期実行の対象を、ヘルスチェック、依存・スキル更新の確認、文書・検証の陳腐化検査、滞留作業の通知などの可逆な処理から選ぶ。コード変更、外部公開、削除、権限変更は既定で自動実行しない。
4. 失敗時のタイムアウト、指数バックオフ、最大試行回数、重複実行防止、通知先、手動再開、緊急停止、監査ログ、秘密情報の扱いを設計する。
5. まず一つの対象リポジトリで最小プロトタイプを動かし、停止・再開、同時実行、権限不足、ネットワーク障害、古い設定、上限超過を含む異常系を検証する。
6. 結果を `HARNESS_SPEC.md` に共通規定として反映し、対象固有の実行環境・コマンド・責任者は対象リポジトリの設定と運用文書に分離する。採用しない自動化や観測は改善台帳に記録する。

## 決定と根拠

- 自動化する範囲と、人間の承認を必須にする境界を決める。→ SPEC §1.3
- 継続実行の状態、失敗時の扱い、停止・再開・更新・撤去の共通契約を決める。→ SPEC §4.2
- 対象リポジトリ固有のスケジューラ、責任者、通知先、コスト上限は共通仕様に埋め込まない。→ T-0004
- 実測が一件だけの運用上の摩擦や自動化候補は、恒久規定にせず改善台帳で扱う。→ T-0006

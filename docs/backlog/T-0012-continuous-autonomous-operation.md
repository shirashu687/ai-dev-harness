# Remoteから手動開始した1課題の自律実行を検証する

## 進め方

### 1. 実行前提を確認する

対象のAGENTS.md、config、requirements、handoverを読み、Remoteから同じプロジェクトへ接続する。既存作業を巻き込まないworktreeまたは独立cloneを準備し、依存解決を先に終える。作業コピーの分離をアクセス権による隔離と呼ばない。

| 項目 | 今回の設定・確認 |
| --- | --- |
| 実行主体・責任者 | 親は既存PCのCodexセッション1件。利用者本人が開始・介入・成果受入、親が子の結果と検証を取りまとめる |
| 稼働 | PC起動・オンライン・アプリ稼働。モバイル切断とPC停止は別に試す |
| 開始記録 | 課題ID、RemoteのセッションID、作業場所、ブランチ、開始SHA、既存差分、製品・モデル・Pythonの確認可能な版とimport元 |
| 利用枠 | 既存契約内のみ。取得できる残量を確認し、不足なら中断。追加API・有料サービス・クレジット購入は行わない |
| 通知 | 標準通知のみ。スマホの通知許可とアプリの設定を確認。必要な端末設定だけ本人が実施する |
| 入力・出力 | 下記の固定依頼・完了条件を入力とし、コード差分、検証・review、worklog、変更宣言を提出する。本流統合・push・公開は受入前に行わない |

通常権限で指定Pythonと必須検証が動くことを無人区間への進入条件とする。起動不能なら原因と次の一手を記録し、別Pythonへの無断置換や権限緩和で進めない。

- 製品要件・完了条件は対象側 `harness/state/journal/T-0008-r2-evidence/request.md` を参照。製品コードの開始版は `8c72c05274bf6880778c9a89a98221b189b57943`。過去の解答・比較結果は実装担当へ渡さない。
- コミット、依頼、独立出力検査 `T-0008-r2-evidence/check_output.py` の現物を確認する。過去の試行パス・モデル・A/B測定条件は継承せず、今回のRemote環境に接続する。検査方法と期待値を開始前に固定する。
- 開始版のハーネスを確認し、不足するT-0004〜T-0006の契約だけ準備段階で接続する。製品コードと回帰テストの開始版は維持し、準備差分を実装差分から分けて固定する。
- 変更範囲はrenderer、必要な回帰テスト、影響する利用者文書と作業記録。テスト追加は既存検証の緩和を許可しない。保護対象の宣言・reviewは既存契約を使う。

### 3. 手動開始から成果提出まで進める

記録は対象の `harness/state/journal/T-0012-remote-single-task.md` に置く。依頼・共通規定は参照し、状態・停止・再開は → SPEC §4.3.2。実装、必須検証、仕様/標準review、報告、retroゲートまでを親が取りまとめる。試行は小課題でも引継ぎ証拠が必要なためworklogを作る。

子を使う場合は独立検査や仕様/標準review等の境界を明示し、識別子・対象・終了状態を記録する。初期設定は環境上限内かつ同時2件まで。同じコード領域の複数実装を行わず、別製品も追加しない。

| 制御 | 今回の実施方法 |
| --- | --- |
| 一時失敗 | 原因・副作用・既存実行を確認して、同一原因への追加試行は1回まで。待機はサービス指定時刻を優先。製品内部の再接続は観測範囲だけ記録し、制御できない回数を上限保証と呼ばない |
| 修正・再検証 | 意図したred→greenとは分け、同一原因への修正2回で改善しなければ中断。判断・権限・枠不足は反復しない。→ SPEC §4.3.1、§4.3.3 |
| 時間 | 一律の時間終了条件は設けず、親・子・テストの時間と停滞の根拠を測る。時間・費用の専用watchdogは今回設置しない。改善しない反復は上記で止める |
| 重複防止 | 再指示は課題ID・セッション・作業場所を照合して既存実行へ戻す。専用ロック・キューDBは作らない。アプリ外の同時書込みを防ぐ機械的保証はなく、検知したら停止する |
| 停止・再開 | 通常停止はworklog保存と子・コマンドの終了確認。即時停止で保存前に止まった場合は再開時に現物から復元。旧実行の停止不明のまま再起動しない。→ SPEC §4.3.2 |
| ホスト不通 | 不通中の操作・通知・自動復旧は保証しない。復帰後に未保存分と旧実行を照合して手動再開する |

以上の回数・同時実行の上限は試行の初期設定であり、製品設定による強制済みとは扱わない。開始時に記録し、変更が必要なら理由と影響を残す。利用枠は親・子を合算し、再開でリセットしない。

### 4. 離席・通知・停止・再開を演習する

通知と停止を非破壊の小さな確認で先に試す。その後、コード課題の正常完了を1回確認し、別の試行コピーまたは同課題の途中状態で中断・再開を演習する。再演を製品修正2件と数えず、正常経路と障害演習を分ける。

| 識別子 | 手順・合格条件 |
| --- | --- |
| remote-preflight | Remoteから対象・版・環境を確認し、指定Pythonと必須検証が動く |
| remote-unattended | スマホから固定依頼を開始してスマホを閉じても処理が進み、工程ごとの「続けて」やPC操作なしで差分・検証・review・報告が揃う |
| notification-delivery | 完了と要介入を各1回発生させ、スマホの受信時刻を本人が確認。通知・開いた課題・worklogの実状態が対応する。ターン終了通知だけを課題完了にしない |
| stop-and-resume | Remoteから停止し、親・子・コマンドの状態を確認。保存差分とworklogから具体的な次工程を実行。子を使った場合、その停止が不明なら未合格 |
| duplicate-and-drift | 再指示で重複実装が起動しないこと、演習用の別差分・古い設定を与えると照合で止まることを確認 |
| failure-and-budget | 意図した非ゼロ終了、一時失敗、権限不足、枠不足の演習入力で、再試行上限と中断・4値・次の一手を確認。実認証失効や枠の使い切りは行わず、模擬確認の限界を記録 |
| host-unavailable | 保存点を作った隔離演習でアプリ終了またはホスト切断を行い、復帰後に現物照合して手動再開。PC電源断を試していなければその復旧は未確認とする |
| independent-output | 事前固定の出力検査でID一意性・目次対応・既存動作を確認。実装担当の自己申告だけで合格にしない |

標準通知が届かない場合はOS・アプリ設定と提供機能を調べ、理由と代替確認を残す。常時画面を見れば気づく状態を合格にせず、Discord等を自動的に追加しない。

### 5. 検証・評価と終了処理

実コマンドの正本は対象 `harness/project/config.md`。変更後の既存全件テスト、必要なOKF index/lint/index-check、変更宣言検査、固定比較点からの仕様/標準review、独立出力検査を行う。CIとClaude Codeは本試行の合格条件に含めず、未実行をローカル成功から補わない。

| 評価 | 記録・今回の基準 |
| --- | --- |
| 成果適合 | 製品完了条件・必須検証・review・独立出力検査を満たす |
| 自律性 | 正常経路で工程を進める再指示・PC操作が0回。開始・最終受入・意図した介入は別集計 |
| 誤報・重複・権限逸脱 | 確認範囲内で各0件。宣言成功を権限強制の証拠にしない |
| 通知 | 完了・要介入が各1回到達し、対応課題へ戻れる。発生から受信の時間を測る |
| 停止・復旧 | 要求から終了確認、再開指示から次工程開始までの時間を測る。子の取り残しと停止後の重複変更がない |
| 再試行 | 原因・工程・回数・前後の結果を残し、設定した上限内である |
| 時間・利用量・費用 | 親の経過時間と子の合計時間を分け、取得できる利用量・枠変化を記録。欠測は不明。新規課金操作がないことを確認し、共有契約の消費と金銭費用を混同しない |

1課題の正常試行と異常系の件数・成功件数を示し、少数例を長期稼働率へ一般化しない。測定から工程時間・委任数・再試行設定の見直し案を示す。実観測は既存retro/台帳に接続し、意図した失敗演習だけを摩擦件数へ加算しない。→ SPEC §7.1。

成果は対象のT-0012 worklogにまとめる。config/handover/verify-reportに不足が実証された場合だけ必要な接続を追加する。専用ランナー・Bot・自動復旧コードは作らない。試行が終われば次課題を起動せず受入へ渡す。変更した試行設定は記録した旧値へ戻せるようにし、他作業の差分・既存Remote接続・worklog・台帳を撤去しない。保管は → SPEC §7.4。実行中の製品・環境変更は対象版へ記録し、影響する確認をやり直す。

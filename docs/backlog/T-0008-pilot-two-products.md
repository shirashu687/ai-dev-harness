# 代表作業3件と2製品で実証する

## やりたいこと

小さな不具合修正、通常の機能追加、中断を伴う作業を一件ずつ行い、Claude CodeとCodexで同じ完了契約が機能するか確認する。

## 背景・現状

ファイルを置いただけではハーネスの有効性は分からない。実作業で、導入前または部品なしの基準と比較し、品質を落とさず手戻りが減るかを測る。

## 進め方

三件の代表作業を着手時に一件ずつ選び、同じ開始条件で可能な比較を行う。完了適合、人の修正、探索反復、検証誤報、スキル起動、所要、文脈負担を記録する。

利用者の追加指示（2026-09-06）により、各候補の採用待ち・比較条件の承認待ち・各試行の人の受入待ちを廃止する。進行管理担当が一件ずつ根拠を確認して選定し、実装・検証・独立review・集計まで進め、最後に詳細HTMLレポートを提出する。これはT-0008の隔離実証の委任であり、対象製品の恒久的な仕様変更・本流への統合・改善策の恒久採用への包括的承認ではない。

| --- | --- | --- |

| 実装担当luna | C1、C2、B1、C3前半、C3後半をそれぞれ履歴を引き継がない実行文脈で処理 | 差分・検証結果・必要なworklogを保存して進行管理担当へ返す |

実装・確認のサブエージェントへの委任を今回の手順とする。利用可能なら履歴なしのサブエージェントまたは独立CLI実行を使い、製品・モデル・起動方式・実行IDを記録する。共有ディレクトリの衝突を避けるため各作業場所を明示し、A/Bは別checkoutへ隔離する。C3後半には前半の会話を渡さない。実装担当には評価側の結果・相手の解答を渡さず、比較成果物を読むことを依頼範囲に含めない。共有ファイルへアクセス可能な構成は隔離の限界として記録する。

サブエージェントで確認した場合は「サブエージェントの新規文脈での再開」と記し、独立したデスクトップセッションの実証と同一視しない。C3は新規文脈・作業状態の現物照合・次の一手実行を必須とする。独立実行を起動できない場合、同じ会話で演技して成功にせず実行不能とする。人にセッション作成や依頼文の転記を日常手順として要求しない。必須操作を人に頼む必要がある場合は、依存しない試行を先に進め、必要操作をまとめて示す。

判断依頼が必要なのは、利用可能な権限では実施不能、認証が必要、実在する候補が見つからない、既存要求が相互矛盾し解釈を決められない、隔離実証の範囲を超える変更が不可避な場合に限る。待つのは依存部分だけ。取得可能な事実や既決事項を再質問しない。commit・push等は既存許可と対象規約に従い、外部公開・本流統合は今回の完了条件に追加しない。

### 一件ずつ選ぶための記録と選定条件

進行管理担当は次の一件だけを調査し、以下を評価worklogへ記録して開始する。人への候補提示と返答待ちは不要。

1. 試行ID、作業名、対象版。バグなら再現入力・期待結果の根拠・実際の結果、機能なら既存文書や実際の利用経路に根拠のある不足と解消する利用場面。
2. 変更する振る舞い、対象外、変更予定の領域、小／通常とした理由。既存の公開動作を破壊しない、局所的で可逆な候補を選ぶ。
3. 外から確認できる完了条件と検証方法。実装前に固定し、既存テストに加えて再現例・入出力例で今回の期待結果を検証する。
4. 選定理由と見送った有力候補の理由。比較対象ならA/B条件、C3なら中断地点。実装担当が結果を見て条件を緩めない。

バグを人工的に埋め込まず、不要な機能を作らない。根拠のある候補がなければ当該試行を未実行として不足を記録し、他の実施可能部分を進める。対象チケットの作成は対象規約を読み、既存 `.venv` のPythonで `-m okf_devkit.cli new backlog` を使う。IDは生成結果に従う。候補実装は隔離場所に保持し、本流へ自動統合しない。

### 各試行の実行手順

1. 両repoの入口、現行SPEC、本タスク、対象config/requirementsを読む。作業場所・完全な開始SHA・既存差分・製品・実モデル・ツール・権限・環境を記録する。lunaが起動できなければ無断で別モデルへ代替せず実行不能とする。
2. 採用済み依頼・対象外・完了条件を固定する。比較ペアは同じ文章と開始SHAを使う。結果を見て条件を緩めない。
3. 作業場所を確保して実装する。比較側は別checkout等へ隔離し、同じ作業ツリーへ重ねない。Python依存と作業ディレクトリを確認し、元repoを誤って検査しない。
4. 小作業は直接修正と短い報告を許容する。観測用記録のために計画・grilling・full retroを強制しない。通常作業は必要な判断、実装、reviewへ進む。→ SPEC §4
5. 対象configの必須検証を実行し、失敗を修正して必要な再検証を行う。通常・中断作業は開始SHAから仕様軸／標準軸reviewを行い、未コミット・未追跡の対象も含める。
6. 独立確認担当が固定条件と実行証拠を照合する。指摘があれば修正・再検証・必要な再reviewへ戻る。人の受入待ちを挟まない。未解決指摘は失敗または限界として残す。
7. 統合する成果物と比較専用の成果物を区別し、同じ修正を二重統合しない。証拠を保存するまで隔離成果物を捨てない。確認済みSHAと結果を評価worklogへ記録する。

開始時のコマンド確認用（正本は対象config）:

```text
.venv/Scripts/python.exe tests/run_all.py
.venv/Scripts/python.exe harness/project/check_changes.py --base <試行開始の完全SHA>
# コード変更時
.venv/Scripts/python.exe -m okf_devkit.cli affected --base <試行開始の完全SHA>
# OKF文書変更時
.venv/Scripts/python.exe -m okf_devkit.cli index --write
.venv/Scripts/python.exe -m okf_devkit.cli lint
.venv/Scripts/python.exe -m okf_devkit.cli index --check
```

保護対象変更には当該開始SHAに対応する `.changes.json` を作る。CI test/smokeは実結果を別記し、ローカル成功で代用しない。今回の詳細化では対象テスト・試行を実行していない。

### B1の比較条件

- 対象作業の実装前に同じ開始コミットからA/Bを準備し、準備差分を別に記録する。比較対象、実施順、入力、製品・モデル・設定・ツールを固定する。
- Bで外すのは自前ルート表・作業手順・worklog・retroへの案内や要求の接続。上流スキル、プロジェクト知識、必須検証・制約、権限、検査コードは維持する。入口に混在する制約はBでも読める形で保持し、具体的なファイルとhunkを保存し、独立確認担当が制約の維持を照合する。包括的なハーネス削除は行わない。
- 両実装担当を過去会話を引き継がない新規lunaセッションにする。相手の解答・結果を渡さない。Bに評価タスク全文や外した手順を必読として渡さない。Bが自発的に同等手順を使った場合は妨げず観測する。
- 観測者の記録項目は両側で揃える。進行管理担当の学習と選定による偏りは限界として記録する。片側で発見した追加要件を片側だけへ渡さない。要件変更が必要なら比較を無効とし、条件を揃えた再試行を1回まで行い、なお成立しなければ比較不能として報告する。
- 同じ受入条件・検証・reviewで品質を確認する。片側だけの検証省略、環境やモデルの不一致、解答混入、実行不能は比較不能とする。
- 1組から一般的・統計的な優位を断定しない。評価対象は自前案内・手順の接続の追加効果であり、製品間の性能比較ではない。

### C3の中断・再開

採用時に「再現確認とテスト追加まで終え、実装は未完」等の中断地点を実際の作業に合わせて固定する。中断のために本番へ不具合を埋め込まない。予定されたTDDのredと計画的中断自体は摩擦に数えない。

1. 前半担当が対象handover手順に従い、同じworklogへ開始SHA・最新HEAD・既存／今回の差分・未追跡ファイル・決定への参照・4値の検証・残作業・妨げ・具体的な次の一手を保存する。
2. 作業場所とworklogの絶対パスを含む再開入力を保存し、前半を終了する。
3. 進行管理担当が履歴なしの新しいluna実行を起動する。過去会話は渡さず、入口とworklogの参照だけを渡す。後半担当は現物を照合して差異を記録し、次の一手から完了まで進める。
4. 記録欠落で人の補足が必要だった場合、既決事項の再質問や不要な再探索を記録する。必要な現物照合・状態変化後の再検証は不要な反復に数えない。
5. 別セッション再開の成立と成果物の条件適合を別に確認する。同じセッションの継続や引継ぎ文を書いただけでは成功にしない。

### 記録の正本と観測方法

評価全体は対象 `harness/state/journal/T-0008-pilot-two-products.md` に置く。試行一覧、選定根拠、比較条件、指標、結論、Claude保留、次の一手を管理する。各作業の要件は対象チケット、状態は対象configに従うworklogへ置き、評価側から参照する。小作業でworklog省略可能なら短い報告を評価側へ保持するが、保護対象変更の宣言で必要なら作成する。

比較の固定入力、切断差分、成果物差分/SHA、検証の必要な出力とreviewを再確認できる参照を残す。会話全文・巨大ログ・認証情報は保存しない。改善観測は対象ledgerを正本とし、評価側は台帳IDを参照する。

| 項目 | 記録・数え方 |
| --- | --- |
| 条件 | 試行ID、チケット、依頼、完了条件、作業場所、開始/終了SHAと残差分、製品・実モデル・設定・ツール、開始/終了日時 |
| 完了適合 | 条件ごとの期待／実際、テスト・CLI出力・差分・review、独立確認の結果と日付。人の受入は未実施と明記し、AI自己採点だけにしない |
| 人の修正 | 既決要件の欠落や誤りに対する独立した修正要求の回数と概算時間。同じ要求の再掲は二重計上しない。選定・起動操作・新規要望は別欄 |
| 探索・質問の反復 | 記録済み情報を見落として繰り返した探索・質問の件数と具体的な根拠。必要な現物照合・再検証は除外 |
| 検証の誤報・漏れ | 実行と報告の不一致、必須検証の欠落を独立事象ごとに記録。テスト失敗それ自体と区別 |
| スキル | 期待する適用条件と実起動、未発動・誤発動・重複の根拠。小作業の正当な未起動は異常にしない |
| 所要・文脈 | 実作業と人待ち/中断待ちを分離。トークンは取得可能時のみ。入口の行数・文字数、一覧省略警告、不要な読込の例 |
| 摩擦・結論 | retro判定、台帳ID、未確認範囲、比較の有効性、次の一手 |

観測不能を0にしない。0には確認範囲を添える。事象はその都度短く記録し、記憶から回数・時間を作らない。

### 最後に提出するHTMLレポート

正本は対象の評価worklogと参照証拠とし、HTMLは再生成可能な閲覧用成果物にする。対象 `harness/state/journal/T-0008-pilot-two-products.html` に出力し、初回依頼者へ絶対パスのリンクを渡す。既存OKFのHTML生成規約はdocsバンドル向けであり、今回のバンドル外worklogは一回限りのローカル生成処理でHTML化してよい。恒久CLIや依存パッケージを追加しない。生成に使った入力と手順をworklogへ記録する。

HTMLはUTF-8・日本語・外部CDN不要の単一ファイルとし、CSSを内包する。根拠となる文章・表・必要な出力抜粋はファイル内に含め、別セッションの会話を読まなくても理解できるようにする。ローカル証拠リンクは補助であり、リンクを開けないと結論が分からない構成にしない。

| レポートの節 | 必須内容 |
| --- | --- |
| 結論と実施範囲 | Codex分の実施状況、Claude保留、合格／不適合／未実行／実行不能の内訳。部分結果なら冒頭に明示 |
| 何をなぜ選んだか | C1/C2/C3/B1の実際の作業、選定根拠、対象外、事前固定した完了条件 |
| どのように実施したか | 作業場所、対象SHA・準備差分、製品・実モデル・ツール、実行ID、実施順、C3中断地点・再開方法 |
| 各試行の詳細 | 入力、期待結果、実際の結果、検証コマンド・終了コード、レビュー指摘と修正、残差分、証拠参照。検証結果はSPECの4値を保持 |
| 比較 | A/Bの維持条件と差分、条件の一致確認、品質・手戻り・探索・スキル・文脈・所要の実測表、比較不能や取得不能の理由 |
| 自律性 | 人への依頼と理由・回数・概算時間、独立確認担当の指摘・修正、どこまで人なしで進められたか。人未評価を明示 |
| 限界と次の一手 | 少数試行・共有環境の限界、未実行CI、Claude保留、未解決事項、改訂候補と台帳ID、必要な人の操作がある場合だけ具体的内容 |

進行管理担当はHTMLを実際にブラウザで開き、冒頭の結論、長い検証表、比較、証拠、末尾の未完事項が読めることを確認する。文字化け、横幅の崩れ、切れた内容、4値の色だけに依存した表示がないことを確認し、Markdownの試行数・数値・状態と照合する。表示できなければ表示確認を実行不能と記録し、生成済みと表示検証済みを区別する。今回はレポート仕様の詳細化であり、実証結果を装うHTMLは作らない。

全試行を終えられない場合も部分結果HTMLを提出する。「レポート提出済み」と「Codex分完了」と「T-0008全体完了」を分け、人の最終閲覧・承認はレポート提出の終了条件にしない。

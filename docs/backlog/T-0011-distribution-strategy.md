# 配布方式と保守責任を比較検討する

## やりたいこと

npx/npm、Python CLI、Codex・Claude Codeのプラグイン等を比較し、別リポジトリへ配る方式と公開範囲を決める。実装や公開は、このタスクでは行わない。

## 背景・現状

現行仕様は、導入先が増えて手作業負担が実測された場合にプラグイン化を優先する仮説を置いている。一方、公開レジストリを使う配布は、依存関係、脆弱性対応、更新停止時の告知など継続的な保守責任を伴う。維持できない方式を先に採用せず、実測と保守可能性を基に判断する必要がある。

2026-09-07時点で、記録と現物から確認できる実導入先は `okf-devkit` の1件。T-0013は完了しているが、T-0009の実導入・演習は未着手である。T-0009の詳細化は本検討と並行して進んでいる。移行時の検査失敗と修正は記録されているものの、導入全体の人の作業時間、反復する誤り、実運用での更新負担は未測定。fixtureでの操作検証やテスト実行秒数を、導入件数や手作業負担の実測に置き換えない。根拠は [T-0013](/backlog/T-0013-extract-distributable-core.md) の検証記録と移行worklog、[T-0009](/backlog/T-0009-second-repository-rollout.md) の進捗を参照する。

配布元GitHubリポジトリはT-0013で既に公開・取得確認済み。本タスクで検討する公開範囲は、追加するパッケージやプラグインの配布先・利用者への対応範囲である。

現行の [導入・保守手順](/project/harness-distribution.md) には全5操作があるが、AIへそのまま渡す依頼文はない。配布版の案内はT-0013の結果参照までで、将来の「更新して」という依頼から目的版を選ぶ継続的な案内は未整備。導入済みの現在版は `harness/install.json` から確認できる。依頼の入口と版選択の説明を補えば十分かを先に評価し、専用CLIが必要だとは未実証の段階で断定しない。

## 進め方

2026-09-07の利用者からの検討開始依頼により、T-0009に先行してgrillingによる要件整理と一次資料の比較を進める。製品化の採用判断にはT-0009の実証結果を照合し、着手トリガーは → SPEC §9.3。Gitからの直接導入を基準として、npx/npm、Python CLI、Codexプラグイン、Claude Codeプラグインを次の観点で比較する。

- 導入、更新、版固定、巻戻し、撤去のしやすさ
- 対応するエージェント、OS、リポジトリ構成
- 依存関係と攻撃面、配布元の侵害時に受ける影響
- 脆弱性受付、修正版公開、廃止告知を継続できるか
- 公開配布、限定配布、公開しない運用の差

比較結果から「採用」「限定利用」「延期」のいずれかを選び、共通規定だけを `HARNESS_SPEC.md` へ反映する。試作が必要な場合も、候補を一つか二つに絞った最小検証に留める。

一次資料の事実と未確認点は [配布候補の調査資料](/project/distribution-options-research.md) に置く。採用判断は本タスクに記録し、調査資料を仕様の正本にしない。

検討の依存関係は、利用者・保守枠（Q1・Q2）→追加便益（Q3）→初回の入口・版選択（Q4〜Q6）→方式比較・必要時保守・タスク分割（Q7）とした。Q7では利用者がプラグイン化を別タスクで扱う意向を示したため、文書入口と製品化を分けて引き継ぐ。

- 公開レジストリへの登録やプラグイン公開は、この比較タスクの範囲外とする。→ T-0011
- 実装候補は、保守責任を継続できると利用者が判断したものだけにする。→ T-0011
- 本比較で最初に対象とするのは利用者本人が管理する複数リポジトリ。共同開発者や不特定多数の利用を初期要件に含めない。利用者回答Q1（2026-09-07）。→ T-0011

- 初回の依頼・推奨配布版の規定は利用者回答Q4〜Q6（2026-09-07）を反映した。→ SPEC §9.1.4
- プラグイン化は別タスクで扱う。既存のT-0010をその実装先として保持し、現行Git配布の文書入口はT-0014へ分ける。利用者回答Q7（2026-09-07）。→ T-0011

### 比較判断

今回の判断は、**追加方式の製品化を「延期」し、既存Git配布を使うAI向けの入口を文書として整備する**。プラグイン化を取り消す判断ではなく、T-0010で扱う作業として保持する。各方式の仕様上の根拠・未検証範囲は [比較資料](/project/distribution-options-research.md) を参照する。

| 候補 | 今回の判断 | 利用者要件に照らした根拠 |
|---|---|---|
| 現行Git固定SHA＋明示手順 | 継続利用 | 既に5操作がある。URL付き依頼と推奨版への導線を補う案を、追加の配布実装なしで検証できる |
| npm配布＋npx/npm exec | 製品化を延期 | 1コマンドでの手動操作は初期目標ではなく、CLI・Node/npm・harness操作の実装を維持する追加便益が未実測 |
| Python CLI | 製品化を延期 | 現行手順でPythonを使うことと、配布用CLIを継続保守することは別。既存照合器と依頼文で足りるかを先に確認できる |
| Codexプラグイン | 製品化を延期 | 事前登録や管理画面からの操作は初期要件になく、製品用の包装・更新とharness操作の接続を追加する便益が未実測 |
| Claude Codeプラグイン | 製品化を延期 | 同上。scope・version・cache等の製品差も保守対象になる |

### 必要時保守と実装への引継ぎ

| 項目 | 本比較での扱い |
|---|---|
| 利用者・担当 | 本人が配布版の選定と必要時の修正を担当し、AIが調査・差分・検証を補助する。定期リリース・定期点検・応答期限の約束は設けない |
| 製品・環境 | 共通方針はCodex・Claude Code、Windowsを含む環境（→ SPEC §1.4）。T-0009は同タスクで合意したCodexの範囲で依頼からの導入を確認し、Claude Codeの未実行範囲は区別して残す |
| 公開範囲 | 現在のGitHub配布元を使う。新しいレジストリ登録、プラグイン公開、他者向けのサポート窓口は追加しない |
| 初回の入口・推奨版 | → SPEC §9.1.4。実装先はT-0014 |
| 導入・更新・巻戻し・撤去 | → SPEC §9.1.3 / §9.1.4 / §9.2 / §9.2.1。操作手順の実装済み部分はT-0013、入口からの実証はT-0014とT-0009で区別する |
| 問題の発覚・保守の休止・終了 | → SPEC §9.1.4。本比較の担当者は本人で、定期の受付・点検や応答期限は設けない |

脅威として比較するのは、配布元や推奨版の記録の改変、実行するコード・外部依存の不具合、導入先の手修正との衝突である。固定SHAとハッシュは版・内容の照合に使い、安全性の審査そのものとは分ける。実行前に固定版の照合器・反映処理を読む既存手順を使い、上流スキルは自身の出所と更新経路で確認する。Git案でも既存のGit・PowerShell・Pythonと照合器の実行は残る。

文書入口の実装は [T-0014](/backlog/T-0014-ai-distribution-entry.md) へ切り出した。T-0009でURL付き依頼からの導入を試し、人の追加回答回数・概算作業時間・再試行を記録するための接続をT-0014で扱う。T-0009が先行した場合は本体の導入結果と入口の検証を区別する。T-0010は引き続き → SPEC §9.3 の条件待ちとし、今回の比較を参照して再評価する。本タスクの成果は比較と規定・バックログ更新であり、入口の実装・実プロジェクトへの導入・公開は含まない。

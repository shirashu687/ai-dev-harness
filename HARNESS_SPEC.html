三つの原則【確定】

  1. ファイルだけで始める。段階1〜2の実体はプレーンな Markdown とディレクトリ構成のみ。ツールは、実測された摩擦を根拠にしてからしか作らない。

役割が欠けている場合の既定の配置は次の通り。何もない状態から始めるなら、この形をそのまま作る。

<プロジェクト>/
├─ AGENTS.md                    ← 入口の正本(プロジェクト所有・1枚のみ)
├─ CLAUDE.md                    ← @AGENTS.md 取込+Claude固有差分(プロジェクト所有)
└─ harness/
   ├─ core/                     ← 将来の共通化候補。汎用の書き方のみ。段階3で配布側所有になる
   │  ├─ procedures/
   │  │  ├─ verify-report.md    ← 手順: 検証と報告
   │  │  └─ handover.md         ← 手順: 中断と引継ぎ
   │  ├─ templates/
   │  │  └─ worklog.md          ← 作業記録の統合テンプレート
   │  └─ policy/
   │     └─ requirements.md     ← 必須制約(利用者のみ編集。denyで保護)
   ├─ project/                  ← プロジェクト所有。共通更新で触らない領域
   │  ├─ config.md              ← コマンド・対象範囲・必須検証・例外
   │  └─ extensions/            ← 独自手順・独自スキルの置き場(最初は空)
   ├─ state/                    ← 作業記録。配布対象外。コミットして引継ぎに使う
   │  ├─ journal/               ← 1作業1ファイル(YYYY-MM-DD-題名.md)
   │  └─ archive/               ← 完了後90日で移動(R9の既定値)
   └─ ledger.md                 ← 改善台帳(プロジェクト所有)
  • core/ に置いてよいのは、別のプロジェクトへそのままコピーしても嘘にならない文章だけ。プロジェクト名・コマンド・パス・内部事情が混ざるものはすべて project/ へ。この規律が段階3の抽出コストを決める。
  • state/journal/ はコミットする(マシンをまたぐ引継ぎに使うため)。大きなログ・生成物は .gitignore し、記録には所在だけ書く。機密・認証情報はどこにも書かない。
  • ファイル数を増やす変更(手順の追加、スキル化)は、台帳の候補として記録してから行う(第1節・原則3)。

# 手順: 検証と報告

1. harness/project/config.md の「必須検証」表のコマンドを順に実行する。
2. 各結果を作業記録の検証記録表へ記す。

4. 「報告(要約)」の4項目(達成/確認済み/未確認/判断が必要)を埋める。
5. この手順を使ったら、報告末尾に確認符号〔VR〕を記す。

6

運用フロー

6.1日々の作業

  1. 作業の規模を AGENTS.md の表で選ぶ。小さな変更に計画書・独立レビュー・新規テストの一律追加を求めない(設計方針書 7.1・9.3)。
  2. 通常以上の作業では journal/ に記録を1枚作り、完了条件を先に書く。
  3. 実装後、「検証と報告」手順を実行する。報告は記録の要約節で完結させる。HTML等の別形式は、説明が複雑なときだけの選択肢とする。
  4. 摩擦(繰り返した探索、誤った検証、不要な質問、誤発動)を感じたら台帳へ1行。その場でルールを増やさない。
  5. 影響の大きい変更では、独立した確認を挟む。現環境では Codex CLI への依頼が「実行製品を差し替えられるレビュー役」(設計方針書 7.4)の最も安価な実装になる。使用した実モデルが確認できない場合は不明と記録する。

6.2変更の二層方針【確定】

層対象要求される手続き
軽量 プロジェクト局所で可逆な変更(config の追記、手順の文言調整、extensions への追加) 台帳に1行書いて、実作業でそのまま試す。比較実験は不要。効かなければ戻して結果を記す
厳格 コアへの昇格、必須制約・権限・完了条件に触れる変更、スキルの新設 第10節の比較(現行/候補/可能なら部品なし)を経てから採用。振り返りからの自動反映は行わない

この二層により、利用者が既に許可している通常作業を止めずに(設計方針書 10.4)、危険な変更だけに評価の関門を置く。

6.3記録の寿命【確定】

  • 完了した作業記録は90日で archive/ へ移す。台帳の採用・却下済みの行は年1回まとめて末尾の「済」節へ畳む。
  • 繰り返す症状は台帳の回数加算で表現し、長文を毎回書かない。
  • 実行ログ・スクリーンショット等の重い証拠はコミットせず、記録には所在と要約だけ書く。

# 必須制約

このファイルの変更は通常の実装修正と区別し、利用者が行う。
強制点が「運用」のみの項目(◇)は運用ルールであり、破られる前提で監視する。

| ID | 制約 | 強制点 | 強制の設定・確認方法 | 既知の限界 |
| --- | --- | --- | --- | --- |
| REQ-1 | 必須検証の失敗・未実行を成功として報告しない | CI(無ければ運用◇+独立再検証) | CI で必須検証を実行する。CI が無い場合のみ、採用判断・マージ前に別セッションで再実行 | CI に無い検証は運用頼み。再検証を省くと無力 |
| REQ-2 | このファイルと config.md の必須検証表を、エージェントが書き換えない | 製品設定 | Claude Code: settings.json の deny(下記)。他製品: 差分レビュー(運用◇) | denyは任意のサブプロセス経由の書込に及ばない(V10) |
| REQ-3 | 許可されていない外部送信・権限拡大をしない | 製品設定/実行環境 | 各製品の権限設定・サンドボックスの有効化を確認 | 製品ごとに段階2で実機確認 |
| REQ-4 | 記録・配布物に認証情報・機密・無関係な個人情報を入れない | 運用◇ | 共有・配布前の目視。台帳・記録のテンプレートに書かない欄を設けない | 運用ルール扱い |

  "permissions": { "deny": [ "Edit(./harness/core/policy/**)" ] }
※ deny は deny→ask→allow の順で最初に評価される(V10)。段階1の対象 okf-devkit は
  CI(ubuntu・windows × Python 3.11・3.13)を持つため、REQ-1 の強制点は当初から「CI」。

ホスティングのアカウント開設や共同開発体制の構築はハーネスの対象外のままとするが、既に存在する CI・ブランチ保護を強制点として使うことは対象内とする(R6)。CI が無い間の REQ-1 の水準は「deny による定義ファイル保護+独立セッションでの再検証」である、と明示しておく。

9

配布・更新・撤去(段階3)

本節は段階3で実装する設計であり、段階1〜2では読むだけでよい。専用の配布CLI・トランザクション機構は作らず、git のコミット単位を配布の原子性として使う(審査記録第4節丙)。

9.1形態

  • コアを harness-core リポジトリへ抽出し、タグで版付けする。版名は日付+連番(例: 2026.09.0)【確定】。同じ識別子から常に同じ内容が取得できることを最優先とする。
  • 導入は「タグの内容を harness/core/ へコピーし、harness/install.json を書き、1コミットで入れる」。更新・巻戻しも同様に1コミット(巻戻しは git revert か旧タグの再導入)。
  • 入口(AGENTS.md 等)への接続行は人が追加する。ツールを作る場合も検査(あるべき行の有無の報告)まで(R7)。
harness/install.json導入記録(最小形。ハッシュ等は必要が実測されてから追加)
{
  "source": "〈harness-core リポジトリの場所〉",
  "version": "2026.09.0",
  "commit": "〈タグの指すSHA〉",
  "installed_at": "2026-09-15",
  "managed": ["harness/core/"],
  "overrides": [
    {
      "path": "harness/core/procedures/verify-report.md",
      "base_version": "2026.09.0",
      "reason": "〈上流反映待ちの修正内容〉",
      "ledger": "K-007",
      "review_at": "次回更新時"
    }
  ]
}

overrides が宣言付き上書き(R5)である。宣言のある管理対象ファイルの改変は正当な上書きとして扱い、宣言のない改変だけを更新時の競合とする。台帳IDを書くことで、共通側に同じ修正が入った版へ更新するとき「この上書きは不要になった可能性」を機械的に列挙できる(共通側の変更履歴にも対応する台帳IDを1行書く)。

9.2更新の手順

  1. 新しいタグの内容を取得し、現在の harness/core/ との差分を確認する(導入時タグとの三者比較。git のツリー比較で足りる)。
  2. 宣言のない改変が見つかったら競合として止め、三つの出口から選ぶ——(a) 上流を採用して改変を捨てる、(b) 改変を overrides に宣言して保持する、(c) 手動でマージする。
  3. 差分(追加・変更・削除・上書きとの重なり)を確認してから、コピーと install.json の更新を1コミットで入れる。
  4. 代表作業を1件流し、入口からの到達と必須検証を確認する。スキルの発動条件・出力形式が変わる版では、文章だけの変更でも動作を確認する。
  5. 問題があれば git revert。state/・project/ は管理対象外なので巻戻しの影響を受けない。

9.3撤去の手順

  1. 削除候補は「install.json の管理対象であり、かつ宣言なしで改変されていないもの」だけ。改変されたものと overrides は一覧にして利用者の判断へ回す。
  2. project/・state/・台帳・入口ファイルは残す。入口の接続行の削除は人が行う。
  3. 撤去後にプロジェクト本来のビルド・テストが通ることを確認して完了とする。

評価の最小実装

評価は厳格層の変更(6.2)にだけ適用する。専用基盤は作らず、記録は台帳と作業記録で足りる。

比較の条件

  • 比較対象: 現行版/候補版。廃止判断のときは「対象部品なし」を加える。初回導入時のみ「ハーネスなし」も1回測って基準線を残す。
  • そろえるもの: 依頼文・開始時のリポジトリ状態(同一コミットから開始)・製品とモデル・利用可能なツール。片方の回答を他方に見せない。
  • 安全条件(必須検証・権限)は「なし」側でも外さない。
  • ばらつきが疑わしい重要な判断だけ複数回流す。全比較の複数回実施は要求しない(H4 で実コストを測って調整)。

11

作らないもの【確定】

以下は「まだ作らない」の規定であり、禁止ではない。トリガーが実測されるまでは着手しない(R2)。トリガーが起きたら台帳に候補として記録し、厳格層の手続きで導入する。

本節は新規作成の抑制であり、導入先に既にある自動化の撤去を求めるものではない【確定】。既存のフック・スクリプトはそのまま使い、保守負担が疑わしいものだけを台帳の観測に入れる。

作らないものいまの代替再検討のトリガー
設定の組み立て・生成レイヤー、設定スキーマと競合検証ツールプレーンなファイルと目視層が2つ以上になり、実際の競合を2回経験した
検証のラッパースクリプトコマンド手動実行+4値の転記転記の誤りが観測された(H3)
スキル(SKILL.md)入口からの明示参照発見・呼出の摩擦が台帳に記録された
